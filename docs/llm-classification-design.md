# LLM-классификация для Sofi — дизайн (без кода)

Статус: дизайн на ревью. Код не пишется. Цель — заменить хрупкий regex-слой классификации пониманием свободного текста на LLM, с единым источником правды для «что записать» и «какая роль». Строго по Владу; конфликт «наши идеи vs Влад» → Влад.

## Проблема (корень багов этого этапа)
Решение «запись» и «роль» принимают **три расходящиеся детерминированные эвристики**:
- `classify_entry` ([bot.py:2068](../bot.py)) — что и писать ли (log_type);
- `detect_intent` ([bot.py:458](../bot.py)) — роль/контекст-пак отдельно;
- `food_like_message` ([bot.py:3008](../bot.py)) — второй путь записи еды в `handle_message`.

Они работают на пересекающихся, но не одинаковых regex → расходятся (ложные записи, пропуски, рассинхрон роль↔запись). Interim-эвристика `68533fb` зашила стоп-кровь и довела заплатку, но архитектура остаётся хрупкой.

## Шаг 1 — сверка с Владом (цитаты)

Влад строит систему на **понимании свободного текста моделью**, а не на regex:

- Setup-гайд: «Коуч — пишешь "съел омлет и творог" → он считает калории, белок, показывает остаток на день» (`health-os-setup-guide.md:9`); «пишешь по-русски» (`:168`).
- Транскрипт звонка: «современные языковые модели хорошо понимают калораж каких-то блюд… есть файлы, в которые он пишет и потом сам же их читает» (`vlad kooklev.md:1266`); про фото — «он распознаёт, записывает» (`:1250`); «какие-то паттерны действительно может определить и сказать мне» (`:1354`).
- **grep/regex у Влада — для базы знаний, не для классификации:** «грэп… по ключевым словам… находит строчки и подтягивает» (`:478`, `:462`).
- Принципы: «Еду записывать из свободного текста: …калории и белок **только если пользователь дал данные или они есть в контексте**» (`vlad-principles.md`); «Если данных нет, прямо скажи `данных нет` и попроси самый маленький полезный ввод».

**Вывод:** LLM-классификация прямо соответствует замыслу Влада. Regex-слой классификации — отклонение (в дизайне Влада его нет; grep он применяет только к knowledge). Конфликта нет — наоборот, LLM-подход возвращает систему к Владу. Консервативная запись («только если данные есть/в контексте», «нет данных → спроси») — прямое требование Влада к поведению классификатора.

## Шаг 2 — аудит пайплайна (read-only)

Поток одного текстового сообщения (`handle_message` [bot.py:2968](../bot.py)):
1. `append_log_entry` ([bot.py:2090](../bot.py)) → `classify_entry` решает log_type и **сразу пишет** файл.
2. `detect_intent` **отдельно** выбирает роль и контекст-пак.
3. `food_like_message` ([bot.py:3008](../bot.py)) — **второй путь записи еды**, если `classify` не записал.
4. Ответ: уже есть LLM-вызов `call_anthropic(text, role/entry_type, daily_log)` — behaviorist [bot.py:3039](../bot.py), general [bot.py:3082](../bot.py). **Один вызов на сообщение**, когда задан `ANTHROPIC_API_KEY`.
5. Детерминированные форматтеры (`format_meal_response`, `format_training_*`) строят ответ для meal/training без LLM — используются и в no-API / ошибка-ветке ([bot.py:3072-3093](../bot.py)).

**Ключевое:** LLM-вызов для ответа **уже происходит** → структурированную классификацию можно сложить в тот же вызов без второго round-trip.

**Переиспользуемо:** контекст-пак (`build_*_context`), форматтеры meal/training (кормить полями от LLM), no-API ветка (детерминированный фолбэк), существующий enum интентов (meal/training/sleep_recovery/biomarkers_imaging/behaviorist/general) — чтобы downstream-загрузка контекста и форматтеры остались без изменений.

## Шаг 3 — дизайн

### 3.1 Где в пайплайне: один комбинированный вызов (рекомендация)
- **(A) Два вызова** (классификатор → ответ): + чистое разделение; − удвоение латентности/стоимости, два места сбоя.
- **(B) Один вызов** (структура + текст ответа в одном, через tool-use/JSON): + нет лишнего round-trip (ответный вызов и так есть), один источник правды; − промпт сложнее.

**Рекомендация — B.** Ответный LLM-вызов уже в пайплайне ([bot.py:3082](../bot.py)); классификация ложится в него «бесплатно» по латентности и одним местом устраняет три расходящиеся эвристики.

### 3.2 Схема структурированного вывода
Через tool-use (надёжнее свободного JSON). `intent` — из **существующего** enum, чтобы переиспользовать контекст-пак и форматтеры:
```
{
  "intent": "meal|training|sleep_recovery|biomarkers_imaging|behaviorist|general",
  "loggable": true|false,                 // писать ли факт
  "log_type": "meal|weight|sleep|training|none",
  "extracted_fields": {                    // ТОЛЬКО то, что явно дано
    "meal":     { "description", "calories?", "protein_g?", "fat_g?", "carbs_g?" },
    "weight":   { "kg" },
    "sleep":    { "hours", "quality?" },
    "training": { "name?", "exercises?", "duration_min?", "rpe?" }
  },
  "confidence": 0.0-1.0,
  "reply_text": "..."                      // ответ пользователю
}
```

### 3.3 Код владеет записью
Модель **только решает и извлекает поля**. В файл пишет **код** (валидация типов/диапазонов: вес 30–300 кг, сон 0–16 ч, калории ≥ 0; единицы; дедуп). Модель файлы напрямую не редактирует — в Telegram-боте это и так делает код; детерминированнее и безопаснее. Соответствует Владу (он про понимание/адаптацию, не про то, кто пишет байты).

### 3.4 Единый источник правды для роли
`intent` из одного вывода заменяет `detect_intent` + `classify_entry` + `food_like_message`. Корневое расхождение этого этапа («classify сказал meal, intent — behaviorist») исчезает по построению: роль и решение о записи приходят из одного вывода.

### 3.5 Консервативная запись (служит «не писать, когда не надо»)
Контракт в промпте: `loggable=true` **только** для явного свершившегося действия («съел/сделал/взвесился N»); намерение/мнение/вопрос/план → `loggable=false`. При `confidence` ниже порога или неоднозначной единице → не писать, задать **один** уточняющий вопрос («нет данных → спроси» по Владу). Это прямо реализует кейсы A (не писать) и B (реальный факт писать) из behavior-audit.

### 3.6 Сбой / невалидный вывод / нет API
- **Невалидная структура / нет нужных полей:** fail-safe — **не писать** (не портить лог), вернуть мягкий ответ/уточнение.
- **Нет `ANTHROPIC_API_KEY` / вызов упал:** LLM недоступен → ответ тоже не сгенерить, НО детерминированная ветка ([bot.py:3072-3093](../bot.py)) уже логирует еду и форматирует ответ оффлайн.
- **Судьба interim-regex (`68533fb`): ОСТАВИТЬ как детерминированный фолбэк** для no-API/ошибки. Он даёт оффлайн-логирование (еда/тренировки/вес) и стоп-кровь; удаление лишит бота оффлайн-функциональности. Рекомендация: **LLM — основной путь, regex — фолбэк**. Пересмотр сноса — только после долгой обкатки LLM в проде.

### 3.7 Латентность / стоимость
Один вызов на сообщение (как сейчас для ответа) — без прироста round-trip. Текущая модель `claude-3-5-haiku` (env `ANTHROPIC_MODEL`) достаточна для классификации + короткого ответа; tool-use надёжнее свободного JSON. Контекст для классификации держать **узким** (directives + profile), не раздувать. Стоимость ≈ как сейчас.

### 3.8 Eval вместо unit-тестов
LLM недетерминирован → бинарные unit-тесты не годятся. Существующий харнесс (`tests/test_classify.py`, 34 кейса, `1350df1`→`6e8ab73`) превратить в **eval**: те же кейсы (A/B/C/MIXED/ADVERSARIAL/CONTROL/intent-7/P4) гонять через LLM-классификатор, мерить **pass-rate**; регресс-гейт = порог (например ≥ 0.95 на наборе и **100% на safety-критичных**: «не писать факт» из A и consistency из C). Прогон N раз для оценки дисперсии. Детерминированный фолбэк (regex) продолжает покрываться старыми бинарными тестами.

### 3.9 Безопасная выкатка — shadow-режим
1. **Shadow:** LLM-классификация считается **параллельно** с regex, прод-решение остаётся за regex; расхождения (regex vs LLM) логируются на живом трафике владельца. Прод не меняется.
2. Анализ расхождений → подстройка промпта/порогов.
3. **Switch:** прод → LLM, regex → фолбэк.
4. **Откат** — env-флагом, мгновенно к regex.
